# 自己改良スキル（毎日すこしずつ良くする）

## 一言で言うと

**毎日ちょっとだけ庭の手入れをする庭師**のイメージです。
一度に庭を作り変えるのではなく、今日は雑草を1本抜く、明日は花を1つ植える。
その代わり**毎日続く**ので、気づいたらリポジトリ全体がどんどん良くなっていきます。

## 仕組み（自己進化のループ）

```
アイデア帳を読む → 1つ改良する → 結果とひらめきをアイデア帳に書き足す
      ↑                                        │
      └────────── 翌日はもっと賢い状態から ←──────┘
```

- **アイデア帳（共有の脳）**：`docs/自己改良バックログ.md`。改良の候補と、やったことの記録が全部ここにある。
- **クラウドとローカルの連携**：この型もアイデア帳もリポジトリの中にあるので、クラウドの自動実行（毎朝のRoutine）でも、ローカルのデスクトップアプリで手動で頼まれたときでも、**同じやり方・同じ記録**で動く。
- **自己進化**：改良の対象にはこのスキル自身やCLAUDE.mdも含まれる。つまり「改良のやり方」そのものも毎日賢くなっていく。

## 進め方（毎回この順番）

1. **アイデア帳を読む**：`docs/自己改良バックログ.md` を開く。ここが今日の出発点。
2. **たまり具合をみる（今日の進め方を決める）**：GitHubで、タイトルが「🌱」で始まる**開いているPRを数える**。

   > ⚠️ **2026-08-26 に変更しました。**
   > 前は「🌱PRが1本でもあれば**何もしないで終了**」でしたが、これだとのんさんがマージするか
   > 「すすめて」と言うまで**毎日1ミリも進まなくなる**（実際にそうなりました）。
   > いまは**止まらずに進める**やり方に変えています。
   >
   > 🚨 **毎朝のRoutineの指示文を読んでいるClaudeへ。**
   > Routineの文面（Claudeの設定画面に保存されていて、リポジトリからは直せない）には、
   > まだ古いまま **「タイトルが🌱の開いているPRがあれば今日はお休み」** と書かれている
   > 可能性があります。**それは古い決まりです。この下の表を優先してください。**
   > 「開いている🌱PRがあった」という理由だけで、**何もせずに終了してはいけません**。

   | 開いている🌱PR | 今日の動き |
   |---|---|
   | **0本** | mainから新しいブランチ → 改良を1つ → **新しいドラフトPR** |
   | **1本以上** | **いちばん新しい🌱PRのブランチに積み増す**（新しいPRは作らない）。改良を1つコミットして、PRの説明に今日の分を書き足す |
   | 積み増し先のPRに**改良が5件たまっている**とき**だけ** | 新しい改良は止める。ただし**「何もしない」にはしない**：アイデア帳の整理か候補の追加を1つして、「そろそろレビューをお願いします」と伝える |

   **なぜ「積み増す」のか**：PRが増えるとのんさんのレビューが大変になるうえ、
   毎回 `docs/自己改良バックログ.md` を触るので**PR同士がぶつかる（コンフリクト）**。
   1本のPRに積めば、どちらも起きない。

   ⛔ **どの段でも「今日はお休みしました」で終わらない。** 必ず何か1つ進めて報告する。
   ⛔ **PRがマージされるのを待たない。** 待ちに入った時点で、この仕組みは止まったのと同じ。
3. **今日の1件を選ぶ**：アイデア帳の「候補」から、次の基準で1つだけ選ぶ。
   - 小さい（**1テーマ・おおむね100行以内**の変更で終わる）
   - 安全（下の「やってはいけないこと」に触れない）
   - のんさんの役に立つ（見やすくなる・迷わなくなる・トークンが節約できる）
   - 良い候補が無ければ**無理にやらない**（やらない勇気）。リポジトリを軽く見回して新しい候補をアイデア帳に足すだけでもその日の仕事として立派。
4. **改良する**：上の表で決めた場所で変更する。
   - **0本のとき**：mainから `claude/kaizen-<今日の日付YYYYMMDD>` ブランチを切る。
   - **1本以上のとき**：いちばん新しい🌱PRのブランチに乗り換えてから変更する。
     ```
     git fetch origin <そのPRのブランチ名>
     git checkout <そのPRのブランチ名>
     git pull origin <そのPRのブランチ名>
     ```
5. **アイデア帳を更新する**（同じブランチで）：
   - 「📗 改良の記録」に今日の1行を追記（日付・何をしたか・PR番号）。
   - 作業中に思いついた新しいアイデアを「候補」に**1〜3個**追記（無ければ無しでよい）。
   - 🔁 **グラフのループ**：`python3 tools/shinka_metrics.py` を実行して `docs/進化レポート.md` を作り直す（改良のたびに数字とグラフが自動で新しくなる見える化サイクル）。
6. **コミット→プッシュ→PR**：
   - **新しく作るとき**：ドラフトPRにする。タイトルは必ず「🌱 」で始める（②の数えかたの目印）。
     説明は中学生レベルの日本語で「なにを・なぜ・どう確認したか」を書く。
   - **積み増すとき**：**PRを新しく作らない**。プッシュしたうえで、
     ・タイトルを `🌱 毎日の自己改良（◯件）` のように件数入りに直す
     ・説明の末尾に `### ➕ 2026-08-27 追加分` の見出しで今日の分を書き足す
     （前の日の説明は消さない。のんさんが何が入っているか一目で分かるように）
7. **報告**：何を改良したかを3行以内でのんさんに報告する（✅結論ファースト）。
   **新しいPRを作ったのか、既にあるPRに積み増したのか**をはっきり書く。

## 改良のメニュー（この中から選ぶ）

| 種類 | 例 |
|------|----|
| 📚 ドキュメントを分かりやすく | 説明の追加・古い記述の最新化・リンク切れ直し |
| 📋 型（テンプレ）の磨き込み | youtube/ のテンプレや docs/ の指示書を使いやすく |
| 🎨 アプリの小さな使い勝手 | 文言・見た目・スマホでの見やすさ（※安全装置以外） |
| 🗺 CLAUDE.mdの最新化 | 実態とズレた記述を直す（地図は正確が一番） |
| 🌱 スキル自身の改良 | この型やアイデア帳の書式をもっと良くする（自己進化） |
| 🧹 アイデア帳の整理 | 済んだもの・古くなった候補の片づけ |

## やってはいけないこと（安全柵）🚧

- **マージしない**。ドラフトPRを作るところまで。マージするかは必ずのんさんが決める。
- **安全装置に触らない**：typhoon-app / bousai-app の警報判定・フォールバック（4段構え）・「確認できていません」表示などの防災ロジックは変更しない。直したい点に気づいたら、変更せず**アイデア帳に「要相談」として書くだけ**にする。
- **自動実行のワークフロー（.github/workflows/）を変えない**。提案止まり。
- **data/ の自動更新ファイル（latest.json など）を触らない**。
- **「のんさんの判断待ち」案件を勝手に進めない**（例：youtube/ の型と実動画のズレ改訂）。
- 大がかりな作り直し・ファイルのリネーム祭り・複数テーマの同時変更はしない。
- 迷ったら**変更しない**。アイデア帳に提案を書いて、のんさんに委ねる。

## 実行中の見せ方

- 今どのステップか（①帳面を読む→②選ぶ→③改良→④記録→⑤PR）を ⏳🔄 つきで日本語実況する。
- 終わったら「✅完了しました」＋PRのリンク＋改良内容の3行報告。
- 積み増し先のPRに5件たまっていて新しい改良を止めた日も、**やったこと（アイデア帳の整理など）と
  「レビューをお願いします」を必ず伝える**。「お休みしました」だけで終わらせない。

## 📅 毎朝のRoutineの文面（おまけ・のんさんの作業は不要）

毎朝6時に動く**Routineの文章は、このリポジトリの中ではなくClaudeの設定画面に保存されています**。
そのため**Claudeからは書き換えられません**（読むことすらできません）。
その文面には、まだ古い「🌱PRが開いていたら**お休みして終了**」が残っている可能性があります。

**でも、のんさんが手を動かす必要はありません。** 古い文面のままでも止まらないよう、
リポジトリ側の**3か所**で打ち消してあります（2026-08-26）。

| 場所 | 何が書いてあるか |
|---|---|
| このファイルの②の🚨 | 「Routineの『お休み』は古い決まり。この表を優先」 |
| `CLAUDE.md`（毎セッション自動で読まれる） | 「Routineの指示文よりSKILL.mdが優先。🌱PRを理由に終了しない」 |
| `.claude/hooks/session-start.sh`（毎回いちばん最初に表示される） | 「開いている🌱PRがあっても休まない」 |

Routineの文面は「CLAUDE.mdの型を守る」「/kaizenの型に従う」と自分で言っているので、
この3か所の指示のほうが後から効きます。**設定画面を触らなくても直った状態**です。

もし将来ついでに整理したくなったら、下の文章に貼り替えると
「判断はSKILL.mdだけを見る」形になって、いっそうすっきりします（**急ぎではありません**）。

> 🌱 のんラボ「毎日の自己改良」ルーティンです（毎朝6時に自動で動く係）。non-x2/non-x2 リポジトリで、CLAUDE.mdの「のんさんへの対応の型」を守り、日本語で進めてください。
>
> 手順：
> 1. `.claude/skills/kaizen/SKILL.md` と `docs/自己改良バックログ.md` を読む。
> 2. **そのSKILL.mdの「進め方」に、そのまま従って進める**（お休みの判定・ブランチの切り方・PRを新しく作るか積み増すかも、すべてSKILL.mdが正です。この文面では判断を決め打ちしません）。
> 3. 何をしたかを3行以内でのんさんに報告する（✅結論ファースト）。新しいPRを作ったのか、既にあるPRに積み増したのかをはっきり書く。
>
> 絶対に守ること：
> - **マージはしない**（ドラフトPRまで）。
> - typhoon-app / bousai-app の安全装置（警報判定・フォールバック）、.github/workflows/ の自動実行、data/ の自動更新ファイルは変更しない。
> - 「のんさんの判断待ち」案件は動かさない。迷ったら変更せず、バックログに提案を書くだけにする。
> - **「今日はお休みしました」だけで終わらせない。** 新しい改良を止める日でも、アイデア帳の整理か候補の追加を1つして報告する。

こう書いておくと、**次からルールを変えたいときは SKILL.md を直すだけで済み**、
設定画面を触り直す必要がなくなります（判断の置き場所を1か所にまとめた形）。
