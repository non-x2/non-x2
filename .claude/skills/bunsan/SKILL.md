# 分散（bunsan）— 助手に仕事を分けて任せるスキル

## これは何をするスキル？

大きな調べ物や作業を、**助手（サブエージェント）**に振り分けるための型です。

例え話：のんさんが分厚い資料を10冊読まないといけないとき、全部自分で読むと大変です。
でも「アシスタントに3人手伝ってもらって、それぞれ数冊ずつ読んで**要点だけ報告してもらう**」
やり方にすれば、のんさん自身が読む量はぐっと減ります。

助手（サブエージェント）に仕事を頼むと、助手が読んだ大量のファイルは**助手の手元に残ったまま**で、
本体（このいまの会話）には**結果の要約だけ**が届きます。だから本体のトークン（会話の容量）を節約できます。

Claude Codeでは、Task という道具で助手を起動します。同時に何人か頼みたいときは、
1回の指示の中でTaskを複数回呼び出す（そうすると並行で動きます）。

---

## ① 分けてよい仕事／分けてはいけない仕事

### ✅ 分けてよい（助手に任せてOK）
- 調べ物・下調べ（複数ファイル、複数リポジトリの確認など）
- ドキュメントの下書き作成
- コードレビュー・チェック
- 複数ファイルの一括確認（表記ゆれチェック、フォーマット統一など）
- 独立した検証（他の作業に依存しない動作確認・見直しなど）

### 🚫 分けてはいけない（本体だけでやる）
- **同じファイルを2体以上の助手が同時に書き換える作業**
  例え話：同じノートを2人が同時に別のページのつもりで書いていたら、実は同じページを取り合っていた、という事故が起きます。触ってよいファイルは必ず助手ごとに分ける。
- **git のコミット・プッシュ・マージ**
  助手が別々にコミットすると履歴がぐちゃぐちゃになります。これは必ず本体（このいまの会話）だけが行う。
- **のんさんへの確認が必要な判断**
  公開する・消す・マージするなど「戻しにくい」判断は助手に丸投げしない。助手には調べる・作る・見るところまでを頼み、判断そのものは本体からのんさんに確認する。

## ② モデルの選び方の目安

助手を起動するとき、作業の重さに合わせてモデルを選びます。指定できる場合は下の目安で選び、
指定できない場合は既定のモデルのままでよいですが、**その場合もどのモデルが動いたかは報告してください**。

| モデル | 向いている作業 | 値段イメージ |
|---|---|---|
| `haiku` | 決まりきった単純作業（一覧を作る、形式をそろえる、表記ゆれチェックなど） | いちばん安い |
| `sonnet` | ふつうの調べ物・文章作成・普通のレビュー（迷ったらこれ） | 標準 |
| `opus` | 難しい判断・設計・見落とすと危ないレビュー（本番公開前の最終チェックなど） | いちばん高い。ここぞという時だけ絞って使う |

**のんさんへの申告ルール（必須）**：作業が終わったら、どのモデルを何体使ったかを必ず日本語で報告する。
例：「今回は sonnet を2体、haiku を1体使いました」。値段が違うので、のんさんが把握できるようにするためです。

## ③ 助手への指示の書き方（テンプレート）

Task で助手を起動するときは、この型をそのまま埋めて使ってください。とくに太字の項目は**省略しないこと**。

```
あなたは「非エンジニア向けリポジトリ non-x2（のんラボ）」の◯◯担当の助手です。

【作業ディレクトリ】/home/user/non-x2
【ブランチ】claude/〇〇〇〇〇〇（すでに切ってあります。このブランチの上で作業してください）

【言語】必ず日本語で答えてください。専門用語は中学生にもわかる言葉でかみ砕いてください。

【何を読むべきか】
- 次のファイル／範囲だけを読んでください。リポジトリ全体を漁って探索しないでください（トークン節約のため）。
  - 〇〇
  - 〇〇

【触ってよいファイル】
- 〇〇（このファイルだけ編集してください）

【絶対に触ってはいけないファイル】
- 〇〇（他の助手が同時に担当しているので絶対に触らない）
- ※ほかにも「今回このタスクで本体や他の助手が触っている場所」を具体的に列挙する

【やってはいけないこと】
- git のコミット・プッシュ・マージは絶対にしないでください（本体が行います）
- 事実を創作しないでください。わからないことは「わからない」「確認できなかった」と正直に書いてください。

【報告のしかた】
- 結論から先に、簡潔に。長い経緯説明は不要です。
- 「やったこと」「わかったこと・直したこと」「気になる点があれば一言」の3点で報告してください。
- 関連するファイルのパスは絶対パスで書いてください。
```

## ④ よくある組み合わせ（実例）

- **「作る担当」＋「レビュー担当」を同時に走らせる**
  例：片方には新しい下書きを作ってもらい、もう片方には別の既存ファイルを見てもらう、のように**別の対象**を同時に頼む。同じ成果物を同時に作らせて後で選ぶ、というやり方は事故のもとなので避ける。
- **「調べる担当」を複数、別々の角度で走らせる**
  例：1人にはA視点（利用者目線）、もう1人にはB視点（技術的な正しさ）で同じテーマを調べてもらい、あとで本体が両方の報告を突き合わせる。
- **レビュー担当には「問題が無ければ問題なしと明言してください」と必ず書く**
  理由：何か指摘しなければと無理に粗探しをしてしまうことがあるため。問題がないという結論も、立派な報告です。

---

## ⑤ 注意点

- **助手の報告をうのみにしない**。とくに「直しました」「対応しました」系の報告は、本体が実際にファイルを開いて確認する。
- **助手は同時に走ると、互いの変更が見えない**。同じファイルを2体以上に割り当てない。
- **数を増やしすぎない**（目安は**3体まで**）。増やすほど待ち時間もお金もかかる。
