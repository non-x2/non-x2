### 📊 2. 進化レポートの数字が逆走する問題を修正（PR #75）

PR #74 の差分に**減る変更**が混ざっていたのが手がかりでした。

| 項目 | 8/17 02:18版 | PR #74（8/17 21:11版） |
|---|---|---|
| 💾 総コミット数 | 85 | **50** ⬇️ |
| 🔀 マージ済みPR数 | 16 | **9** ⬇️ |
| 📈 グラフ | 直近4日間 | **直近2日間** ⬇️ |

**原因**：クラウドの作業部屋は**リポジトリの履歴を全部は持っておらず**（浅いクローン）、しかも**部屋ごとに量がバラバラ**でした。

| 部屋 | 持っていた履歴 |
|---|---|
| このセッションの部屋 | 149件 |
| PR #74 を作った部屋 | 50件 |
| （検証で作った部屋） | 1件 |

集計が `git rev-list --count HEAD` など**手元の履歴だけ**を数えていたので、**どの部屋で実行したかで数字が決まって**しまい、成長を見るはずのファイルが逆走していました。

**直し方**：数える前に `git fetch --unshallow` で**全履歴を取り直す**ようにしました。心配だった所要時間は**1.4秒**でした。

| | 直す前 | 直した後 |
|---|---|---|
| 総コミット数 | 50〜85（部屋しだい） | **479**（6月10日から全部） |
| マージ済みPR数 | 9〜16 | **66** |
| グラフ | 2〜4日ぶん | **14日ぶん** |

ネットにつながらないときは**黙って少ない数字を出さず**、「今回は全履歴を取れませんでした。実際より少なめです」と正直に書くようにしました。

## 🤔 経緯（なぜその判断をしたか）

### ⭐ BC州の `credit` 欄の仕分け——調査記録の誤りを訂正した

前回の調査記録には「**26台ほどは他所が提供しているカメラ**」とあり、README にも「**足すときは `credit` 欄が空のものだけにするのが安全**」と書かれていました。

しかし**実際に全件を調べたら、話がちがいました**。

| 中身 | 台数 | どうしたか |
|---|---|---|
| 他所が写真を提供（TransLink・Parks Canada・City of Vancouver など） | **34台** | ❌ 取り込まない |
| ただの運用メモ（「太陽光発電なので遅れます」「監視のため向きが変わります」「対面通行中」など） | **48台** | ✅ 取り込む |

`credit` は**提供元専用の欄ではなく、運用のお知らせも混ざる自由記述欄**でした。
**記録どおり「空のものだけ」にしていたら、州が自分で運用している48台を誤って捨てるところ**でした。

→ 「**他所が写真を提供していると読める言い回し**」だけを除く方式にしました
（`provided by` / `courtesy of` / `co-operation with` / `installed and maintained by`）。
安全側に少し広めで、電源提供の2台も除いています。**逆に1台も除かないと、州のライセンスの外の写真を載せてしまう**ため、この線引きが必要です。

### ライセンスも記録を鵜呑みにせず自分で確認した

BC州の公式データカタログのAPIを直接引いて、`Open Government Licence - British Columbia` であることを確認しました。写真URLも**3台で実際に開いて**、本物のJPEGが返ることを確かめてから取り込んでいます（HTTP 200・`image/jpeg`・先頭バイト `\xff\xd8`）。

### 高速道路の区別はしないことにした

アイオワ州は路線名が `I-80` のように高速だと分かりますが、**BC州のデータには高速かどうかを見分けられる印がありません**。
**分からないものを決めつけない**ため、BC州分は全部「一般道」にしました。

### 🛠 途中で見つけて直した自分の不具合

**地域のしぼりこみボタンを足したら、🇺🇸も🇨🇦も両方0台になった。**
原因は、ページに埋め込む**圧縮データに `src`（情報源）の欄が無かった**こと。
配る側（`export.py`）とページ側の読み解く処理の**両方**に `s` の欄を足して修正しました。
→ 実ブラウザのテストを書いていなければ、**気づかないまま公開するところ**でした。

### ダブルタップは「壊れていなかった」

1回目のテストで「反応しない」と出ましたが、**私のテストが遅すぎた**（320ミリ秒の判定を超えていた）だけでした。
時間を正確にして測り直したら正常でした。**テストが失敗したとき、まず自分のテストを疑う**べき例です。

### 🚗 1. 交通量の丸の「押し間違い」を実測で発見して解消

バックログの候補3「72個中17個は当たり判定を広げられていない」を調べたところ、
**もっと重い問題**が隠れていました。

**当たり判定が固定8pxだったので、隣の丸と重なっていた**のです。重なった場所は
「あとから描かれたほう」が勝つので、**指で押した場所といちばん近い丸が食い違っていました**。

画面を2px刻みに **38,976点** 押して確かめた結果：

| | 旧：固定8px | **新：隣に応じて可変** |
|---|---|---|
| 指が届いた点 | 7,591 | 5,001（-34%） |
| ✅ いちばん近い丸が反応 | 6,393 | 4,990 |
| ❌ **別の丸が反応（押し間違い）** | **1,198点（15.8%）** | **11点（0.2%）** |

**約6回に1回、隣の観測点の交通量が開いていた**ことになります。

→ 丸を描くたびに隣との距離を測り、**ぶつからないギリギリまで上下左右それぞれ**広げる方式に変更。
**見た目（丸15px・色・位置）は1ドットも変えていません。**

⚖️ **トレードオフは正直に**：届く範囲は34%狭くなります。それでも採用したのは、のんラボの信条が
「**間違ったデータを黙って見せない**」だからです（警報の扱いと同じ考え方）。
届かなければ「もう一度押す」だけですが、間違ったデータは気づけません。

⚡ 速度も確認：丸1000個（観測点の全数）でも計算は **2.1ミリ秒**（1コマ16.7msに十分収まる）。

### ⭐ 助手の実装を、危うく間違った理由で捨てるところだった

交通量の丸の改良を検品したとき、最初にこう測りました：

> **押せる面積の合計：35,363 → 22,304px²（-37%）** → 「悪くなっている」

さらに私は「当たり判定はCSSで**円**なのに四角で計算しているから削りすぎだ」と考え、
**円で計算し直した自分の案**まで作りました。ところが測ると **14,970px²** で、**もっと悪かった**のです。

ここで測り方を変えました。**画面全体を2px刻みの網の目にして38,976点を押し、
「押した点にいちばん近い丸が反応したか」を数えた**ところ、結論がひっくり返りました。

| | 旧 | 助手の案 | 私の案 |
|---|---|---|---|
| 押し間違い | **1,198点（15.8%）** | **11点（0.2%）** | 2点 |

**面積だけ見ていたら、6回に1回データが食い違う状態を「良い」と判定して残すところでした。**

⭐ 学び：**測る指標を間違えると、正しいものを捨てて間違ったものを残す。**
「良くなったか」ではなく「**利用者にとって何が起きるか**」を測る指標を選ぶこと。
そして**自分の対案が一番悪いこともある**（今回がそれ）。

### 「届かない」と「切れている」を分けた理由

リンクの見張り番を作って最初に走らせたとき、**阪神高速と本四高速が「届かない」**と出ました。
しかし1本ずつ試すと**普通に200が返りました**。8本同時にたたいたせいの誤検知です。

→ 「届かない」ものだけ**時間をおいて1本ずつ確かめ直す**保険を足しました。
これを入れなければ、**生きているリンクを「切れている」と報告するところ**でした。
（8/19の学び「テストが失敗したら、まず自分のテストを疑う」がそのまま効きました。）

### 🔬 追加検証：アイデア帳の「候補2」は間違いだったので却下しました

助手が「丸の間引きが**縦横それぞれ**を見るAND判定なので、斜めに近い2点（例：横6px・縦14px）を
**見逃して見た目が薄く重なる**。円の距離で判定すれば直る」と指摘し、候補2に入れていました。

**実際に作って測ったら、逆でした。**

| | 現行（縦横のAND） | 円の距離に変更 |
|---|---|---|
| 丸の数 | 67 | **84（増える）** |
| 指が届く点 | 5,001 | 5,303 |
| ❌ 押し間違い | **11点（0.2%）** | **89点（1.7%）** |

からくりはこうです。横6px・縦14px の2点を、しきい値15pxで判定すると——

- **AND判定**：`6<15 かつ 14<15` → 両方あてはまる → **間引かれる**
- **円の距離**：`√(6²+14²) = 15.2 > 15` → あてはまらない → **残ってしまう**

つまり **AND判定のほうが斜めに厳しい**（強めに間引く）のです。変えると地図が混み、押し間違いも8倍に増えました。
→ **現行のまま**とし、アイデア帳の候補2は**取り消し線＋却下の理由つき**で残しました
（同じ提案が繰り返し出てこないように）。

⭐ 学び：**アイデア帳の「候補」も、書いてあるだけでは正しさの保証にならない。**
着手する前に、まず**前提が本当か**を1回測る。今回は測ったおかげで、悪化する変更を入れずに済みました。
